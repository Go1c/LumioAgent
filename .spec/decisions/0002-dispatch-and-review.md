# 0002 · 主 loop 只调度不实现;planner / coder / reviewer 三角色与交回物格式

- 日期:planner / coder 于框架初建时确立;reviewer 于 2026-07-03 重新引入并补录
- 状态:生效

## 背景

单上下文既做规划又写代码又自评,上下文膨胀快、自我审查失效——写代码的和验收的是同一个「人」。框架早期曾移除过独立审查环(嫌流程重),但在真实项目(GameFlow)中长期运行后发现:没有独立审查上下文,coder 的「已通过」声称无人证伪,质量问题批量漏到收口之后,返工成本远大于审查成本。

## 决策

- **主 loop 理解目标、拆任务、调度、收口,自己不写代码。** 调度权只在主 loop,子 Agent 不再派活。
- 三个职能角色:`planner`(模糊 → 任务卡)、`coder`(任务卡 → 实现 + 自测)、`reviewer`(交付 → 对抗审查报告)。**实质改动必过 reviewer**——写的人和审的人必须是两个上下文;纯文档微调 / 机械套用可跳过。
- 子 Agent 交回物必须带**验证证据**(命令 + 输出),不得只声称完成;格式定义在 `AGENTS.md`「交回物格式」。
- 失败升级路径:reviewer 退回 → coder 重做;同一问题三次不过 → 质疑方案本身(回 planner 或升级用户)。

## 后果

- 每张实质卡多一次 reviewer 上下文的 token 成本——用豁免条件(纯文档 / 机械改动)控制。
- 取代早期「移除审查环」的决定:当时删掉的是「流程性审查步骤」,这次加回的是「独立对抗上下文」,二者的区别(证伪式、有交回物格式、有升级路径)是这条决策的核心。
- Codex 等单上下文宿主无法真正隔离「写」与「审」——退化为主 loop 按 `reviewer.agent.md` 串行自查,隔离收益打折。与 0001 的宿主不对称同源,已知并接受。
