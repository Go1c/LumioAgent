# Before You Code（执行前协议）

在写任何代码或修改任何文件之前，完成三件事：加载上下文、校准深度、规划输出。跳过这一步等于用过期地图导航——即使方向感再好，也可能走错路。

## 何时使用

- 拿到任务卡，即将开始实现。
- 修改已有模块，但不确定该模块的规范或约定。
- 任何「我知道怎么做，直接开干」的冲动出现时——这正是需要停下来读一遍的信号。

## 操作步骤

### 第一步：加载上下文

**必须读，无条件：**

1. 查 `knowledge/README.md`，找出与本次任务相关的知识文档，逐一阅读。
2. 查 `.spec/skills/`，找出本次任务可能用到的 Skill，读其 `SKILL.md`。
3. 读任务涉及的关键源文件（接口定义、被修改模块的现有实现）。

**为什么无条件：** Skill 和 knowledge 文件编码的是项目级约定与环境约束，这些不在模型训练数据里。不读就动手，等于假设自己的默认行为恰好符合本项目规范——这个假设大概率是错的。不要先判断「是否需要读」，直接读；Skill 本身定义了它覆盖的范围。

### 第二步：校准执行深度

根据任务规模决定投入力度，避免小任务过度设计、大任务草率行事：

| 任务规模 | 特征 | 执行方式 |
|----------|------|----------|
| 小 | 改动 ≤ 1 个文件，逻辑独立 | 直接实现，一次完成 |
| 中 | 涉及 2–5 个文件，有跨模块影响 | 先列改动清单，再逐项实现 |
| 大 | 多模块、多步骤、有依赖关系 | 停下向主 loop 报告，建议用 `task-breakdown` 重新拆卡（子 Agent 不自拆、不派活） |

深度校准的核心原则：**做够、不多做**。任务卡说做什么就做什么，不顺手重构无关代码，不提前为假想需求加抽象。

### 第三步：规划输出策略

动手前确定两件事：

**输出形式：**
- 改已有文件 → 定位到具体位置，最小化改动
- 新建文件 → 确认放到哪个目录、遵循哪种命名约定

**生成策略：**
- 短（< 100 行）→ 一次生成，直接完成
- 长（≥ 100 行）→ 先写结构/骨架，再逐节填充，每节可独立验证

## 快速参考

```
收到任务卡
  → 读 knowledge/ 中相关文档
  → 读 skills/ 中相关 SKILL.md
  → 读任务涉及的源文件
  → 判断任务规模（小/中/大）
  → 决定输出形式与生成策略
  → 开始实现
```

## 注意事项（Pitfalls）

- **别跳过「先读」。** 「这个我懂」不是跳过的理由。项目约定 ≠ 通用惯例，差异藏在 knowledge/ 里。
- **别把「读」变成「收集」。** 读完就用，不要把读到的内容全部复述到回复里。
- **大任务别硬撑一次完成。** ≥ 100 行的实现分段生成，每段可验证，出错成本低。
- **深度校准要诚实。** 低估任务规模是最常见的失误——涉及多模块就承认是「中」，不要当「小」处理。

## 验证

- 动手前，已阅读 `knowledge/README.md` 并打开了所有相关文档。
- 动手前，已确认本次任务是否有对应的 Skill，有则已读。
- 已确定任务规模，并选择了匹配的执行策略。
- 已确定输出放到哪里、用什么策略生成。
