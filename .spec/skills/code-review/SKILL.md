# Code Review（代码审查）

在代码合并 / 交付前，按固定维度逐项审查改动，确保正确、安全、可维护。目标是发现真正的问题，而不是堆砌主观风格意见。

## 何时使用

- coder 完成一项任务、提交前的自查。
- reviewer 对产出做交付前终审。
- 任何代码改动进入主分支之前。

## 前置条件

- 改动已能构建 / 编译通过。
- 相关测试已存在并可运行。
- 能拿到任务卡或改动意图说明（用来判断「改对了没」）。

## 操作步骤

1. **对照意图。** 先读任务卡 / 改动说明，确认这次改动到底要解决什么，再看代码是否真解决了它。
2. **正确性。** 逻辑是否正确？边界条件、空值、错误路径处理了吗？
3. **安全。** 有没有注入风险、未校验的输入、泄露的密钥、缺失的鉴权？外部输入是否当不可信处理？
4. **可维护性。** 命名清晰吗？是否与周边代码风格一致？有没有夹带任务外的改动？
5. **测试。** 新增 / 改动是否有测试覆盖？测试是否真的会因为这个 bug 失败？
6. **定级。** 把发现的问题分为「必须改（红线 / 正确性 / 安全）」和「建议（风格 / 可优化）」，分开列。

## 快速参考

| 维度 | 一句话自问 |
|------|-----------|
| 意图 | 这真的解决了任务卡的问题吗？ |
| 正确性 | 边界和错误路径都处理了吗？ |
| 安全 | 外部输入当不可信处理了吗？密钥有没有泄露？ |
| 可维护 | 风格一致吗？有没有夹带无关改动？ |
| 测试 | 这个改动有对应测试且会因 bug 失败吗？ |

## 注意事项（Pitfalls）

- 别只挑风格毛病而放过正确性 / 安全问题——后者才是审查的重点。
- 别在没读懂改动意图前就下结论。
- 「必须改」和「建议」要分开，否则 coder 分不清优先级。
- 发现同类问题，指出整类，而不是只点一个实例。

## 验证

- 每个维度都过了一遍，没有跳项。
- 给出的每个问题都具体到文件 / 行，并说明为什么是问题。
- 明确产出「放行」或「打回 + 必须改清单」。
